CASES문제 해결
  • DB CPU 는 정상인데 전체 API 가 느려진 이유를 찾았습니다. 고트래픽 파트너의 미션 재오픈 조건을 바꾼 배포 뒤 응답이 12ms 에서 160ms 로 늘고 일부는 60초까지 밀렸습니다. 요청량은 평소와 같고 DB CPU 도 30% 수준이라 DB 는 아니라고 봤지만, connection pool 만 모두 차 있었습니다. 중복 요청 제어가 없어 한 파트너의 반복 요청이 connection 을 계속 물고 있었습니다 — 중복 제거·동시 실행 제한·10초 캐시로 160ms → 9ms. 배포 검증 기준에 DB CPU 만이 아니라 응답 시간과 connection 사용량을 넣었습니다.
  • 제휴사 지면 요청의 31%가 헛것이라는 걸 로그에서 찾아 없앴습니다. 하루치 ALB 액세스 로그 227만 요청에서 preflight 가 31%(하루 40,668건)라는 비율을 먼저 찾았습니다. 액세스 로그에는 요청 헤더가 없어 원인은 알 수 없었고, 헤더 이름만 세는 계측을 잠깐 붙여 확정했습니다 — 모든 요청에 붙던 Content-Type 하나였습니다. GET 은 본문이 없어 의미가 없는데, 붙는 순간 단순요청 조건이 깨져 왕복이 하나씩 더 생깁니다. GET 에서 걷어내고 POST 는 Access-Control-Max-Age 로 캐시해 preflight 94% 감소, GET 은 0건.

전환율 68%→7% 급감, 27개 페이지가 빈 HTML 로 나가던 건을 포함한 네 건의 추적 전문은 포트폴리오에.
