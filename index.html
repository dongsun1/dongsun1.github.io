전환율이 68%에서 7%로 떨어진 원인을 매체별 퍼널에서 찾았습니다

미션 참여 퍼널을 매체·카테고리별로 집계하고 있었는데, 전체 전환율이 평소 45% 수준에서 15%까지 떨어진 구간이 있었습니다. 매체별로 나눠 보니 한 매체만 68%에서 7%로 떨어졌고 다른 매체는 큰 변화가 없었습니다.

같은 기간 그 매체의 상세보기는 약 12배 늘었는데 완료 수는 그대로였습니다. 유입이 는 것이 아니라 참여가 막혀 같은 목록을 반복 조회하는 상태로 봤습니다.

원인은 소진 여부를 판단하는 캐시를 자사 미션 조회 판정보다 먼저 확인하는 순서였습니다. 노출돼야 할 미션이 차단되면서 카테고리 간 재조회가 반복됐습니다.

판정 순서를 바꾸고 전체 조회 결과가 비었을 때만 소진으로 기록하도록 고쳤습니다. 해당 매체 전환율은 66%로 회복해 3주간 유지됐습니다.

콜백 실패도 전환 실패로 잡히고 있었는데, 사유별로 나눠 보니 78.5%가 중복 참여였고 추적 ID 관련은 0건이었습니다. 이후 사유별 카운터로 적재해 진짜 장애와 정상 중복이 섞이지 않게 했습니다.

DB CPU는 정상인데 전체 API가 느려진 이유를 찾았습니다

특정 고트래픽 파트너의 미션 재오픈 조건을 변경한 배포 이후 전체 API 응답 시간이 12ms에서 160ms 수준으로 증가했고, 일부 요청은 최대 60초까지 지연되었습니다.

요청량은 평소와 비슷했고 DB CPU도 약 30% 수준이었지만 DB connection pool이 모두 사용되고 있었습니다.

요청 흐름을 추적한 결과 공용 큐나 중복 요청 제어 없이 동일 요청마다 DB 쿼리가 실행되고 있었고, 특정 파트너의 반복 요청이 connection을 지속적으로 점유하고 있었습니다.

동일 요청에 대해 하나의 DB 호출만 실행하도록 중복 요청을 제거하고, 동시 실행 수를 제한했으며, 10초 캐시를 적용했습니다.

같은 보호 패턴을 외부 파트너 조회 API에도 적용했고, 배포 검증 기준에 API 응답 시간과 connection 사용량을 추가했습니다.

요청의 31%가 헛것이라는 걸 로그에서 찾아 없앴습니다

실사용자 성능을 매체별로 보려고 계측을 직접 만들었습니다. 지면에서 Core Web Vitals 를 표본 추출해 보내고, 서버가 매체별 p75 로 집계합니다. 수집이 지면을 느리게 만들면 재려던 값이 나빠지므로, 수집 코드는 지연 로드해 초기 번들을 늘리지 않았고 지표는 지면이 숨겨질 때 한 번에 보냅니다.

표본을 붙이는 김에 하루치 ALB 액세스 로그(227만 요청)를 열어 매체사 연동 실사용을 셌습니다. 제휴사 지면 요청의 31%(하루 40,668건)가 preflight였습니다.

액세스 로그에는 요청 헤더가 없어 원인을 알 수 없었습니다. 서버에 헤더 이름만 세는 계측을 잠깐 붙여 확정했는데, 원인은 모든 요청에 붙던 Content-Type 하나였습니다. HTTP 클라이언트 기본 설정이 GET 에도 붙이고 있었고, GET 은 본문이 없어 의미가 없는데 붙는 순간 단순요청 조건이 깨져 왕복이 하나씩 더 생깁니다.

GET 에서 헤더를 걷어내 preflight 자체를 없애고, 본문이 있어 피할 수 없는 POST 는 Access-Control-Max-Age 로 캐시했습니다. 같은 계측으로 재보니 하루 40,668건에서 2,265건으로 94% 줄었고, GET preflight 는 0건이 됐습니다.

고치고 나서야 실사용자 기준 "before" 가 없다는 걸 알았습니다. 그래서 API 응답 시간도 같은 파이프라인으로 재기 시작했습니다 — 다음 개선은 전후를 숫자로 말할 수 있게.
